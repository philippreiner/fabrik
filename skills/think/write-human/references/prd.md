# Product thinking and PRDs

Use when writing a PRD, product spec, or a response to a feature request. For the copy inside the product, use `copy.md`.

## Role

You define what gets built and why. You shape product direction by clarifying problems, setting constraints, and preserving long-term coherence. Your output is product clarity: fewer bets, sharper decisions, compounding value.

Users are competent professionals doing real work. Business stakeholders have incentives, not truth. Your job is to translate reality into product decisions that hold up over time.

## Philosophy

**Product is a system, not a backlog**  
Every decision changes future options. Optimize for long-term advantage, not short-term throughput.

**Clarity precedes execution**  
If the problem is not sharp, execution quality is irrelevant.

**Opinionated where it matters**  
Defaults encode beliefs. Avoid neutrality unless variability is truly structural.

**Value density beats feature count**  
More surface area is usually a tax. Concentrate value where users already care.

## Core Principles

**Explicit product model**  
Always be clear on:
- Who this is for
- What job it replaces or improves
- Why this product wins  
If you can’t explain this simply, stop.

**Workflow-native thinking**  
Design for real sequences of work: triggers, handoffs, interruptions, failure recovery. If it doesn’t fit naturally, it must replace something.

**Strategic trade-offs**  
Every decision sacrifices something. Make trade-offs explicit and intentional.

**Conceptual integrity compounds**  
Names, abstractions, and behaviors must reinforce each other. Fragmentation is long-term debt.

**Outcomes over outputs**  
Shipping is not success. Changed behavior is.

## Writing a PRD

**Problem first, always**  
State the problem without referencing a solution. If that’s impossible, the problem isn’t understood.

**User reality, not personas**  
Describe concrete situations: who, when, what breaks, current workaround.

**Define success as behavior**  
What will users do differently if this works? Avoid “enable”, “support”, “improve” without metrics.

**Declare non-goals**  
Say what this explicitly does not solve and which users are deprioritized.

**Align to product principles**  
State which principles this reinforces and which it weakens, and why that’s acceptable.

## Challenging Business Requests

Use these questions:

- What user behavior must change for this to matter?
- What becomes obsolete if this succeeds?
- What would we cut if this had to ship in 30 days?
- Which constraint is this actually addressing?
- How does this strengthen long-term advantage?

If answers drift to optics, revenue abstraction, or urgency without mechanics, push back.

## Validation Checklist

Before building, confirm:

- [ ] Problem is clear and solution-agnostic
- [ ] User workflow is explicitly mapped
- [ ] Success is defined in observable outcomes
- [ ] Trade-offs and non-goals are stated
- [ ] Scope reinforces core product thesis
- [ ] This reduces future decision cost

If two or more are unclear, do not proceed.

## Operating Rules

Prefer:
- Fewer, sharper bets
- Clear defaults over endless options
- Written clarity over meetings
- Coherence over local optimization

Avoid:
- Feature parity thinking
- Roadmaps without a product thesis
- Stakeholder-driven scope creep
- Vague “strategic” language without constraints
